# 단계별 개발 계획

7-E: 등록 주간 보스 기본 목록, API 원문 이름·난이도, 예상/실제 수익 분리, 마지막 정상 목록 및 수동 대체 표시를 구현했다. 기존 관측 이력을 사용하여 migration 없이 수동 선택과 클리어 revision을 보존한다. 합성 검증과 Windows 앱 재실행 검증 결과는 [7-E 보고](STAGE_7E_REPORT.md)에 기록했다. 다음 단계는 사용자 승인 전 진행하지 않는다. 아래 7-D 상태는 이전 단계 기록이다.

7-D 상태: 수동 가격 기능 제거·과거 데이터 보존·스케줄러 등록 관측 검증을 마쳤다. 사용자 제공 보스 12개는 실제 API 등록 보스 이름과 일치했고, 7일 전 등록 난이도 집합도 같았다. 인게임 난이도 대조·초기화 직전/직후 검증이 남아 API 자동 관리 목록 구성과 수동 선택 제거는 보류한다. [7-D 보고](STAGE_7D_REPORT.md)를 바탕으로 다음 검증 범위를 승인받는다. 메소·아이템 및 UI 리디자인은 시작하지 않는다. 아래는 이전 단계 기록이다.

7-C 가격 관리 및 API 완료 관측까지 완료했다. 검증 기록은 각 STAGE 보고서에 있다. 앱 식별자는 `com.mapleledger.app`이다. 사용자 요청에 따라 7-B에 카드 진입·기본 UI를, 7-C에 보스·난이도별 영구 가격 설정과 사용자 확인 API 반영을 포함했다. 다음 단계 승인 대기다. 아래는 자동 실행 목록이 아니다. 각 단계 종료 시 변경·검증·미검증을 보고하고 승인 전 멈춘다. 커밋·푸시는 명시 요청이 필요하다.

확정 정책: 본캐 1개 필수, 본캐 포함 관리 최대 6개, 추가 캐릭터는 동일 계정·월드로 제한한다. 본캐 변경으로 선택이 충돌하면 사용자 확인 후 재설정하며 취소 시 기존 상태를 유지한다. 본캐 변경·선택 해제로 기존 보스·메소·아이템 기록을 삭제하지 않는다.

## 공통 검증 운영

API 응답 확인은 UI 빌드와 분리하고 응답 원문·개인 식별자·인증 헤더를 산출물에 남기지 않는다. 가짜 데이터는 공식 필드 구조만 사용한다. 순수 규칙은 좁은 Rust 테스트, DB는 임시 SQLite와 트랜잭션 검증을 사용한다. 문서/단순 UI 수정마다 전체 앱 빌드와 무관한 회귀 검증을 반복하지 않는다. 실패 원인을 분석한 뒤 해당 검증만 재실행한다. 필요한 검사 도구는 실제 프로젝트 명령을 확인한 뒤 사용하고 존재하지 않는 npm 스크립트를 가정하지 않는다.

## 구현 전에 확인할 사항

- 1단계 확정: 표시명 Maple Ledger, 식별자 com.mapleledger.app, React/TS/Vite + Tauri 2 구성.
- 2단계 확정: Windows Credential Manager와 Windows 전용 keyring 어댑터 사용. API 키는 DB에 저장하지 않는다.
- 4단계 확정: rusqlite(bundled), 사용자 앱 로컬 경로의 단일 본캐 테이블, user_version 마이그레이션. 계정/월드 변경 확인과 식별 불일치 시 설정 보존을 구현했다.
- 5단계 확정: 본캐 포함 최대 6개·추가 선택 순서·revision 저장, 본캐 변경과 선택 갱신의 단일 트랜잭션을 구현했다. 조회 누락은 자동 삭제하지 않으며 키 교체 시 닉네임으로 재연결하지 않는다.
- 7-A 확정: 주간 수동 기록, API는 사용자 수락, 클리어 귀속 수익, 개인액=가격/인원의 정수 몫, 수정 이력 및 미산정 보존. 공식 미확인 가격·파티 예외는 조사 문서의 검증 상태를 따른다.
- 8~9단계: 월드 잔액의 계정 범위, 시작 잔액·정정·취소 및 보스 유효 수익과 잔액 연계, 확장 통계. 보스 판매 추적은 추가하지 않는다.
- 10단계: 지원 Windows 범위, NSIS/MSI/휴대 배포 선택, WebView2 제공 전략, 서명 필요성. 서버 기반 자동 업데이트는 요청 없이 추가하지 않는다.

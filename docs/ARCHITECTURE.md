# 초기 아키텍처 제안

7-D 최신 상태: 수동 가격 UI·IPC·신규 적용을 제거했다. 내장 가격과 당시 스냅샷을 사용하며 과거 수동 가격 스냅샷과 v4 설정 행은 보존한다. 추가 마이그레이션은 없다. registration_flag는 완료 여부와 별개이며 과거 관측의 누락 필드는 미확인이다. 실제 API 2회에서 사용자 제공 12개 보스와 현재/7일 전 등록 난이도 집합의 일치를 확인했다. 인게임 난이도·초기화 경계 검증이 남아 자동 구성은 보류하고 수동 선택을 유지한다. [7-D 보고](STAGE_7D_REPORT.md)를 따른다. 아래 7-C 가격 설정 설명은 당시 구현 이력이다.

상태: 7-C까지 구현했다. 앱 식별자는 `com.mapleledger.app`이다. 최대 6개 카드 대시보드와 수동 주간 보스·정수 수익·revision 이력을 제공한다. 본캐·선택·보스 기록은 SQLite, 카드 상세/이미지는 메모리에 보관한다. 일반 메소 잔액·아이템은 아직 구현하지 않았다.

7-C는 SQLite v4에 보스·난이도별 수동 가격 설정, 별도 스케줄러 관측 및 중복 수락 방지 테이블을 추가했다. 가격 설정 변경은 기존 스냅샷을 바꾸지 않는다. 명시적 오늘 조회 → Rust의 관리 선택·응답 기준일·정확한 이름/난이도/주기 검사 → 관측 저장 → 사용자 날짜·파티·가격 확인 → 기존 클리어 저장 트랜잭션에서 수락하는 흐름이다. 기존 기록과 충돌하면 덮어쓰지 않는다. 기존 Credential Manager와 NexonClient를 재사용하며 스케줄러 자동 조회는 없다. 상세 정책·실제 응답 차이·검증은 [7-C 보고](STAGE_7C_REPORT.md)를 따른다. 아래 7-B 설명은 당시 구현 기록이다.

## 계층과 데이터 흐름

```text
React 화면 → 타입화한 invoke 래퍼 → Tauri Commands
                                      ↓
                              Rust 서비스 / 도메인 규칙
                               ↙                ↘
                    Nexon API 클라이언트       Repository
                            ↓                    ↓
                    넥슨 공식 HTTPS API        SQLite
                                      ↘ Windows 비밀 저장소
```

- React: 설정 입력, 전체 캐릭터 목록, 본캐 및 후보 선택, 카드와 오류 표시. API 키는 입력 중에만 임시 보유하고 저장 후 지운다. API 직접 호출, SQL 실행, 비즈니스 규칙의 최종 판정을 하지 않는다.
- Tauri Commands: 좁은 IPC 진입점, 입력 DTO 검증, 서비스 호출과 안전한 응답 변환. 키 조회 명령이나 임의 URL/SQL 실행 명령은 제공하지 않는다.
- Rust 서비스: 본캐/계정/월드 일치, 최대 6개, 선택 충돌, 캐시와 갱신, 트랜잭션의 책임을 가진다. UI 검증과 별개로 항상 규칙을 강제한다.
- Nexon 클라이언트: 고정 공식 호스트, API 키 헤더 주입, 타임아웃, 응답 변환, 동시 요청 제한, 중복 요청 병합, 제한된 재시도. 키를 디버그 포맷으로 출력하거나 다른 호스트 리다이렉트로 전달하지 않는다.
- Repository: 파라미터화 SQL, 제약조건, 트랜잭션, 캐시와 사용자 기록의 분리. React에서 DB에 직접 접근하지 않는다.
- 비밀 저장소: Rust에서 Windows 사용자 단위 비밀 저장 기능을 사용하고 UI에는 등록 여부만 반환한다. SQLite에는 비밀의 참조와 일반 설정만 저장한다.

시작 시 앱 데이터 경로를 결정하고 본캐 설정을 읽을 때 DB를 열어 필요한 마이그레이션을 적용한다. 저장된 본캐는 목록 조회 없이 복원한다. 전체 API 목록과 장부의 오프라인 캐시는 아직 없다. 키 등록 여부는 OS 저장소에서만 읽고 DB에 복제하지 않는다. 향후 비밀 저장소와 DB 메타데이터를 함께 갱신할 때는 두 저장소 사이의 부분 실패 복구를 둔다. 목록 갱신은 인증된 클라이언트→스키마 검증→메모리 스냅샷 갱신→DTO 반환 순서다. 실패 시 저장된 본캐나 장부 기록을 삭제하지 않는다.

## 저장 모델과 데이터 안전성

- Tauri `app_local_data_dir()` 아래 `ledger.sqlite3`를 사용한다. Windows 확인 경로는 `%LOCALAPPDATA%\com.mapleledger.app\ledger.sqlite3`이며 실행 위치·리포지토리·OneDrive 경로를 사용하지 않는다. 앱 식별자는 출시 후 경로 안정성을 위해 유지한다.
- main_character는 singleton=1 제약으로 본캐 한 행을 유지한다. 5단계는 managed_character(최대 6행, OCID 고유, 위치 0~5 및 본캐 역할)와 selection_state(저장 충돌 검사용 revision 한 행)를 추가했다. API 키와 전체 API 목록은 저장하지 않는다. 7-B는 선택과 독립된 보스 계획·주차·클리어/revision 테이블을 추가하고 PRAGMA user_version=3을 사용한다. 일반 장부·다중 프로필은 없다.
- 본캐와 선택은 프로필 범위에 속한다. 본캐 1개는 필수이며 본캐를 포함하여 최대 6개의 중복 없는 OCID를 선택한다. 추가 캐릭터는 본캐와 동일 계정·월드여야 하며 Rust 트랜잭션에서 검사한다. 본캐를 선택 해제하려면 먼저 본캐 변경 절차를 거친다. 계정과 월드 정보가 없는 캐릭터는 관리 후보로 허용하지 않는다.
- 키 교체로 새 목록의 계정 집합이 달라져도 기존 장부는 삭제하거나 자동 합치지 않는다. 접근 불가 캐릭터는 보존하고 재연결 확인을 요청한다. 비밀 자체를 프로필 ID로 쓰지 않는다.
- 본캐 변경으로 기존 선택 목록과 충돌하면 변경 결과를 알리고 사용자 확인 후 목록을 재설정한다. 취소 시 기존 본캐와 선택을 그대로 유지한다. 본캐 변경이나 선택 해제로 기존 보스·메소·아이템 기록을 삭제하지 않는다. 재설정 후에는 새 본캐가 필수 포함된다.
- 이후 보스 기록·메소 원장·아이템 거래는 별도 테이블로 확장한다. 월드 잔액은 서로 다른 계정을 혼합하지 않도록 계정+월드 범위를 제안한다. 사용자 요구의 월드 단위 표현과 조율한다.
- 금액은 정수 단위로 저장한다. Rust/SQLite 정수 범위를 확인하고 JavaScript 안전 정수 범위를 넘는 값은 문자열 DTO로 전달한다. 7-A 보스 수익은 클리어 시 전량 판매를 가정해 귀속 기간에 반영하며 판매 원장을 만들지 않는다. 수정/해제는 revision을 남기고 현재 유효한 금액만 집계한다. 8단계 잔액 연계는 별도 설계한다.
- 마이그레이션은 버전 순서에 따라 적용하고 성공 후에만 버전을 기록한다. 최초 스키마와 002 선택 스키마를 트랜잭션으로 적용하며 새 버전 DB는 덮어쓰지 않는다. v1→v2는 기존 본캐·기타 데이터를 수정하지 않고 본캐를 관리 위치 0으로 복사한다. 실패 시 DDL·버전까지 롤백한다. 키 설정 등 나머지 화면은 유지한다. 데이터 손실 위험 변경 전에는 일관성이 보장되는 방식으로 백업하며 실행 중 DB 파일 단순 복사를 백업으로 간주하지 않는다.
- singleton·필수 값 제약 및 짧은 트랜잭션을 사용한다. 7-B 보스 관계는 foreign_keys를 연결별 활성화하며 현재 revision 포인터는 지연 FK로 검사한다. WAL은 도입하지 않았다. 저장 성공은 커밋 후 알린다.

### 4단계 본캐 지정 경계

도메인은 OCID로 캐릭터를 찾고 부모 account_id와 world_name을 함께 유지한다. 필터는 두 값의 정확한 일치만 사용하며 닉네임·직업 추측은 없다. 서비스는 마지막 성공 목록과 세대 번호를 메모리에 보관한다. 새 성공 조회 및 키 변경으로 세대가 바뀌므로 오래된 화면의 저장 요청은 거부한다. API 재조회 없이 본캐 지정·필터를 처리하며 전체 목록을 DB에 저장하지 않는다.

`get_main_character`는 본캐와 목록의 일치 상태·필터 결과 및 순서 있는 관리 선택·revision을 반환한다. `set_main_character`는 OCID·목록 세대·기존 본캐 식별자·예상 선택 revision·확인 여부를 받는다. 클라이언트가 보낸 새 계정·월드를 신뢰하지 않고 서비스 목록에서 찾는다. Immediate 트랜잭션 안에서 기대값을 비교하고 변경 확인을 검사한 뒤 본캐와 관리 선택을 함께 갱신한다. 기록 테이블을 삭제하는 SQL은 없다.

저장된 OCID가 누락되면 missing, 같은 OCID의 계정/월드가 달라지면 identity_changed로 안내하고 새 후보를 비운다. 본캐와 선택은 자동 삭제·재연결하지 않는다. 식별자가 일치하면 최신 표시 정보를 사용한다. 재시작 시 마지막 저장 정보와 관리 순서를 복원한다. 확인창 취소는 저장 IPC를 호출하지 않는다. 7-B 보스 이력은 선택과 별도로 보존하며 일반 메소/아이템 기록은 아직 없다.

### 5단계 관리 선택 경계

본캐는 위치 0의 필수 관리 항목이며 추가 선택은 5개까지다. Rust는 1~6개, 본캐 포함, OCID 중복 금지, 동일 계정/월드를 검사한다. 새로운 추가는 현재 본캐와 API 목록의 식별 일치가 확인되어야 한다. 기존 누락·식별 불일치 항목은 마지막 식별 정보를 유지하고 상태를 표시한다. 조회 전 또는 본캐가 조회되지 않는 경우에도 기존 선택 유지·해제는 가능하지만 미검증 캐릭터 신규 추가는 금지한다. 미조회 항목도 6개 상한에 포함한다.

`save_managed_characters`는 OCID 배열의 순서, 선택 revision, 기존 본캐, 선택적인 목록 세대를 받는다. 현재 본캐와 revision을 같은 DB 트랜잭션에서 비교하고 검증 후 선택 행만 교체한다. 본캐는 항상 선두로 정규화한다. 요청한 신규 선택은 Rust 목록에서 메타데이터를 얻으며 기존 미조회 항목만 DB 스냅샷을 재사용한다. 저장 실패 시 전체 롤백하며 다른 저장의 결과를 오래된 화면으로 덮어쓰지 않는다.

같은 계정/월드에서 본캐가 바뀌면 새 본캐를 첫 항목으로 두고 기존 추가의 순서를 유지한다. 새 본캐와 중복된 항목은 제외하고 이전 본캐를 자동으로 추가하지 않는다. 명확한 계정/월드 불일치는 제외하지만 조회 누락만으로는 무효로 단정하지 않아 기존 미조회 추가는 보존한다. 다른 계정/월드는 사용자 확인 후 새 본캐만 남긴다. 이 변경은 본캐와 선택을 같은 트랜잭션에서 처리한다. 장부가 선택 테이블 삭제에 연쇄 삭제되도록 연결하지 않는다.

React는 체크박스 초안과 저장된 선택을 구분한다. 상한에 도달하면 선택되지 않은 항목을 잠그고 기존 추가 해제는 허용한다. 저장 버튼을 눌러야 반영되며 저장 전 변경 취소를 제공한다. 본캐 변경·목록 갱신 시에는 저장된 설정을 기준으로 상태를 다시 구성한다. 별도 순서 편집 UI는 아직 없다.

### 6단계 대시보드·이미지

대시보드와 캐릭터 관리 화면을 분리했다. `get_dashboard`는 관리 선택을 SQLite에서 읽어 순서를 유지한 카드 DTO를 반환한다. 이때 네트워크나 키 읽기는 수행하지 않아 저장 정보로 먼저 표시할 수 있다. `refresh_dashboard_card`는 DB에서 관리 대상·선택 revision을 확인한 후 기존 Rust 클라이언트로 해당 OCID만 갱신한다. OCID를 전달했다고 임의 캐릭터를 조회하지 않으며 전체 목록을 재조회하지 않는다.

기본 정보는 `/maplestory/v1/character/basic`에 필수 ocid와 키 헤더를 사용하고 선택 date는 생략한다. nickname/class/level은 응답에 있으면 반영하고 누락 시 확보한 표시 정보를 유지한다. 응답 world_name이 저장된 월드와 다르면 적용하지 않는다. 이 API에는 계정 ID와 응답 OCID가 없으므로 계정 소속을 추측하거나 닉네임으로 OCID를 재연결하지 않는다. 계정 소속 변경 검증은 기존 전체 목록 관리 흐름을 사용한다.

응답 character_image URL은 HTTPS·정확한 공식 호스트·정적 캐릭터 경로만 허용하고 리다이렉트를 차단한다. 공개 이미지 요청에는 키를 붙이지 않는다. 본문 상한과 PNG/JPEG/GIF/WebP 서명을 확인한 뒤 Rust에서 data URL로 인코딩해 전달한다. 원격 SVG는 허용하지 않는다. React는 이미지 로딩 오류까지 로컬 SVG 자리 표시자로 처리한다. 기존 CSP의 self/data 범위로 표시하며 외부 이미지 origin을 추가하지 않았다.

카드 캐시는 같은 CharacterSession 안에서 클라이언트와 잠금을 재사용한다. 선택에 남아 있고 계정/월드/OCID가 같은 최대 6개만 유지한다. 키 변경·삭제 시 캐시를 비운다. 정상 카드 15분·실패 카드 60초 재사용, 수동 갱신 2초 반복 억제와 같은 이미지 URL 다운로드 재사용을 적용한다. 이는 앱 로컬 정책이며 넥슨 쿼터 수치를 의미하지 않는다. 기본 정보/이미지는 영구 저장하지 않고 DB 테이블과 마이그레이션도 변경하지 않는다.

React 효과는 화면 진입과 명시적 새로고침에만 동작하며 per-card promise 공유로 StrictMode·동시 요청을 합친다. 각 카드의 정보·로딩·오류를 독립적으로 갱신한다. 개별 파싱/네트워크/식별 실패는 다른 카드를 지우지 않는다. 공유 키 오류·429는 배치의 남은 호출을 중단하고 기존 정보를 표시한다. 429 대기 동안 백엔드에서도 재호출을 막으며 자동 재시도하지 않는다. DB 설정과 선택에는 쓰기를 수행하지 않는다.

## 키 저장 선택지

2단계 결정: Windows Credential Manager를 채택했다. `keyring-core 1.0.1`과 `windows-native-keyring-store 1.1.0`을 연결하고 기본 검색 기능을 비활성화했다. keyring 전체 래퍼나 DPAPI 파일 관리는 도입하지 않았다. 아래 비교는 선택 배경으로 유지한다.

1. Windows Credential Manager + Rust 어댑터: Windows 사용자별 저장을 활용하고 앱 DB에서 키를 분리할 수 있다. 어댑터 의존성 및 저장소 오류 처리가 필요하다. 우선 제안이다.
2. Windows DPAPI로 보호한 파일: 별도 보안 저장 서비스 의존은 줄지만 암호문 파일 수명·권한·교체·복구를 직접 관리해야 한다.

평문 파일과 localStorage는 배포 저장 방식으로 사용하지 않는다. 운영체제 사용자 계정에 종속되므로 다른 PC로 장부를 옮기더라도 키는 다시 입력하는 방향이다. 같은 사용자 권한의 악성 프로세스까지 방어한다고 주장하지 않는다.

구현 세부: 고정 target `com.mapleledger.app/nexon-open-api`, 일반 자격 증명, Local 지속성으로 현재 PC와 Windows 사용자에 저장한다. Rust 전용 읽기는 `Zeroizing<String>`으로 감싸고 사용 후 폐기한다. 키 관리 IPC는 `api_key_status`, `save_api_key`, `delete_api_key` 3개이며 boolean 등록 상태만 반환한다. 별도의 목록 조회 IPC에도 키 원문은 포함하지 않는다. OS 저장소 호출은 blocking worker에서 수행하고 Mutex로 같은 키에 대한 동시 접근을 막는다. 오류는 비밀 데이터를 포함할 수 있는 원본 오류를 포맷하지 않고 고정된 코드·안내로 변환한다.

설정 화면은 입력 중 DOM 메모리에만 키를 보유하고 저장 시도·삭제·화면 이탈 시 입력을 비운다. 저장 원문을 복원하지 않는다. 표시/숨김은 새로 입력한 키에만 적용된다. Rust 입력 버퍼는 zeroize로 정리하지만 WebView/IPC/JavaScript의 모든 메모리 복사본 소거를 보장하지는 않는다. 키를 읽는 개발 도구·프로세스 덤프·동일 사용자 권한 악성 코드까지 방어하는 설계는 아니다. 실제 유효성 검증은 다음 단계이며 저장 성공 안내에서 이를 구분한다.

## 오류와 네트워크 정책

공개 오류 DTO는 앱 내부 코드, 사용자 메시지, 재시도 가능 여부로 제한한다. 내부 HTTP 상태와 정제한 원인은 개발 진단에만 사용한다. 원문 응답·헤더·키 입력을 그대로 로그에 넘기지 않는다. 인증 실패, 요청 제한, 네트워크 장애, 응답 불일치, DB 오류, 비밀 저장소 오류를 구분한다. 키 등록 성공과 API 검증 성공은 구분한다.

3단계 목록은 사용자가 불러오기를 눌렀을 때만 요청한다. 화면에 현재 성공 스냅샷과 조회 시각을 메모리 보관하고 네트워크·파싱 실패 시 이전 결과임을 표시하여 유지한다. 인증·키 누락·보안 저장소 오류는 이전 결과를 숨긴다. 설정으로 이동하면 목록 컴포넌트가 해제되어 이전 키의 목록도 제거된다. 자동 조회·재시도는 없다. 백엔드 try_lock 및 프런트 pending/disabled로 중복 요청을 막고 로컬 2초 클릭 간격을 둔다. 이는 넥슨의 공식 제한값을 의미하지 않는다. 429는 초 단위 Retry-After를 적용하며 없거나 날짜 형식이면 60초를 기다린다. 자동 재호출은 하지 않는다. DB 기반 재시작 캐시는 현재 범위에서 제외하고 후속 저장 설계에서 다룬다.

추가된 `load_characters` IPC는 Rust 보안 저장소 읽기→서비스→Nexon 클라이언트 순서로 호출하며 계정 ID를 부모 계정에 유지한 제한된 DTO만 반환한다. 원본의 추가 필드는 버리고 닉네임·직업·레벨의 누락/null은 정보 없음으로 표시한다. 계정 ID·OCID·월드·배열 구조가 없거나 식별자가 중복되면 전체 응답을 안전한 파싱 오류로 처리하고 추측하여 그룹을 만들지 않는다. 계정 ID·월드·이름·OCID 기반 정렬과 React 식별자 키를 사용하며 응답 순서에 의존하지 않는다. UI는 내부 식별자 대신 계정 순번을 표시한다.

HTTP는 reqwest 0.13.5의 기본 기능을 끄고 native-tls-no-alpn만 사용한다. Windows Schannel과 OS 인증서 검증을 이용하며 HTTP/2·쿠키·압축·Rustls C 암호화 제공자·파일 업로드 기능을 추가하지 않는다. HTTPS 전용, 고정 endpoint, 리다이렉트 차단, 민감 헤더 표시, 연결 5초/전체 15초 제한과 본문 2MiB 상한을 적용한다. reqwest 자체 재시도도 끈다. 400 OPENAPI00005는 공식 오류표에 따라 인증 오류로 변환한다. 원본 오류·본문·키는 사용자 메시지에 포함하지 않는다. 기본 정보와 공개 이미지도 같은 전송 제약을 재사용하며 이미지에는 인증 헤더를 보내지 않는다.

자동 초기화는 과거 기록을 지우는 방식 대신 기간 ID별로 새 상태를 표시한다. 앱이 꺼진 동안에는 실행되지 않으므로 시작·절전 복귀·실행 중 기간 경계에서 현재 기간을 계산한다. 7-A 주간 경계는 목요일 00:00 KST이며 월간/일간 콘텐츠는 최초 주간 범위에서 제외한다. 근거와 미검증 예외는 `BOSS_CRYSTAL_RESEARCH.md`를 따른다.

7-A 정책과 저장 설계는 [보스 관리 설계](BOSS_MANAGEMENT_DESIGN.md)에 있다. 7-B에서 수동 기록·계산 스냅샷·현재 revision 집계를 v3로 구현했다. 선택과 독립된 record_characters, character_boss_plans, boss_periods, boss_clear_records/revisions를 사용한다. 카탈로그는 검토된 JSON을 컴파일에 포함하며 판매/범용 원장과 API 관측 테이블은 없다. 상세 검증과 개발 전용 분리 DB/오프라인 UI 점검은 [7-B 보고](STAGE_7B_REPORT.md)를 따른다.

## 의존성 후보와 대안

1단계에는 React/ReactDOM, Vite, TypeScript, React Vite 플러그인, React 타입, Tauri CLI 및 Rust tauri/tauri-build만 구성한다. 현재 Node 22.15와 호환되는 Vite 6을 사용한다. 기본 초기화 외 후보는 다음과 같으며 버전 및 기능은 채택 직전에 확인한다.

| 후보 | 도입 이유 | 대안 및 비용 |
| --- | --- | --- |
| Vite (1단계 도입) | React/TS 개발 서버와 번들 | 직접 구성은 유지보수 증가; 사용자 승인한 스택으로 구성 |
| reqwest (3단계 도입) | Tauri/Tokio와 통합되는 Rust 비동기 HTTPS 클라이언트 | ureq 등 동기 클라이언트는 blocking worker가 필요; 직접 WinHTTP는 FFI 관리 증가 |
| serde/serde_json | IPC 및 API 직렬화 | 수동 파싱은 스키마 오류 처리 부담 |
| base64 (6단계 직접 선언) | 작은 이미지의 data URL 전달·메모리 재사용 | 원격 img URL 직접 표시는 재마운트 시 다운로드와 외부 CSP 설정이 필요; 바이트 배열 IPC는 더 큼. 기존 전이 패키지를 재사용 |
| rusqlite (4단계 도입) | 최소 본캐 SQLite 설정·명시적 SQL·트랜잭션 | JSON은 임시 구조와 이후 이전 비용 발생; sqlx는 현재 단일 설정에 비해 구성 증가 |
| keyring-core + Windows 전용 어댑터 (2단계 도입) | Credential Manager를 통한 사용자 API 키 보호 | Win32 직접 호출은 unsafe 코드 관리 부담; DPAPI는 파일 수명·복구 관리 필요 |

초기에는 별도 전역 상태, 라우팅, ORM, 차트 라이브러리를 선제 도입하지 않는다. 필요한 화면과 병목이 생긴 단계에서 판단한다.

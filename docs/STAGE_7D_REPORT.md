# 7-D — 수동 가격 기능 정리 및 스케줄러 등록 목록 검증

작업일: 2026-10-28 KST. 지정된 AGENTS·아키텍처·개발 계획·보스 설계·가격 조사·7-B/7-C 보고와 API 키 방식 scheduler 요청/응답/components를 확인했다. 최신 사용자 요청에 따라 기존 수동 가격 허용 정책을 대체했다. 외부 maplemate는 사용하거나 참고하지 않았다.

**결론:** 수동 가격 기능 정리는 완료했다. API에서 등록된 보스·난이도를 추출할 수 있고 사용자 제공 보스 12개와 실제 등록 보스 이름도 일치했다. 다만 인게임 난이도 대조와 초기화 직전/직후 검증이 남아 **자동 관리 목록 구성은 보류하고 수동 보스 선택을 유지**했다. 사용자 승인 없이 다른 관리 방식을 도입하거나 수동 선택을 제거하지 않았다.

## 1. 제거한 수동 가격 기능

- 보스·난이도별 수동 가격 입력·수정·해제·설정 폼과 관련 React 상태를 제거했다.
- 기록별 가격 직접 입력을 제거했다. 정정 사유는 기존 기록 정정에 필요하므로 선택 입력으로 유지했다.
- 프런트 가격 설정 DTO/래퍼, Rust 가격 설정 읽기/쓰기, 가격 설정 command 및 메인 창 권한을 제거했다. 새 ClearInput은 manual_price를 받지 않으며 오래된 가격 입력 payload도 거부한다.
- 기존 boss_price_settings 행은 **삭제하지 않지만 신규 계산에는 사용하지 않는다.** 수동 가격을 저장·수정·해제하는 IPC가 남아 있지 않은 것을 실제 앱에서도 확인했다.
- 과거 request_json의 manual_price=null은 중복 요청 비교에서만 호환 처리한다. 저장된 감사 JSON을 갱신하거나 과거 수동 가격을 신규 입력으로 적용하는 기능이 아니다.
- 사라진 폼의 사용하지 않는 CSS 3개 규칙만 제거했다. 색상·폰트·카드 구조·애니메이션 리디자인은 하지 않았다.

## 2. 유지한 가격·버전 구조와 기존 데이터 영향

카탈로그 JSON, DATA_VERSION=`kms-2026-10-28-v1`, CALC_VERSION=`party_floor_v1`, 공식 근거 가격 51개와 미확인 null 3개를 유지했다. 출처·적용일·적용 시점 판정과 당시 가격/개인액/출처/버전 스냅샷을 유지한다. 이번에 내장 가격을 갱신하거나 웹 가격을 재조사·크롤링하지 않았다.

| 대상 | 7-D 동작 |
| --- | --- |
| 신규 클리어 | 적용 시점이 확인되는 내장 가격으로 정수 계산. 없으면 미산정 |
| 기존 수동 가격 설정 행 | v4 DB에 그대로 보존. 신규 기록에는 적용하지 않음 |
| 기존 수동 가격으로 계산된 기록 | 기존 금액·출처·버전·revision을 그대로 표시/합산 |
| 같은 난이도·날짜의 인원 정정 | 당시 스냅샷 가격으로 새 revision을 계산하고 과거 revision 유지 |
| 날짜·난이도를 바꾸는 명시적 정정 | 내장 가격을 다시 판정. 확인 불가 시 새 revision은 미산정이며 이전 revision은 유지 |
| API 완료 반영 | 내장 가격/적용 시점이 확인되지 않으면 수락을 차단하고 기존 기록 유지 |

향후 게임 패치 대응은 내장 가격 자료의 새 버전과 적용 시점을 추가하는 방식이다. 기존 기록의 가격을 자동 변경하지 않는다. 가격 자동 업데이트 기능은 없다.

## 3. 공식 명세 및 실제 API 검증

API 키 방식 `GET /maplestory/v1/scheduler/character-state`를 사용했다. `ocid`로 자신의 계정 캐릭터를 개별 조회한다. `date`는 선택 사항이며 YYYY-MM-DD로 이전 14일 이내 조회가 가능하고 생략하면 오늘이다. 해당 날짜에 캐릭터가 접속하지 않았다면 응답이 없을 수 있다는 명세의 제한을 확인했다. Open ID 방식의 경로/인증을 사용하지 않았다.

관련 명세의 보스 항목은 content_name, difficulty, cycle, list_order_no, registration_flag, complete_flag다. 등록 필드는 인게임 스케줄러 등록 여부, 완료 필드는 완료 여부의 문자열 true/false로 설명돼 있다. 보스 정보는 콘텐츠 완료 시 갱신된다는 설명도 확인했다. 즉시 설정 동기화 지연이나 주간 초기화 시 등록 유지에 대한 보장으로 확대 해석하지 않았다.

기존 Rust NexonClient의 HTTPS·민감 헤더·시간 제한·본문 상한·오류 변환을 재사용한 명시적 ignored 테스트로 실조회했다. 사용자 DB의 관리 캐릭터를 읽기 전용으로 확인했고, 현재 관리 대상이 한 명이어서 다른 캐릭터를 새로 찾거나 조회하지 않았다. 사용자에게 받은 보스 이름 목록은 내부의 표준 보스 이름과 대조했다. 캐릭터 이름·OCID·계정·월드·API 키·인증 헤더·원본 응답은 보고서나 테스트 출력에 기록하지 않았다. 테스트 출력은 집계와 비교 결과뿐이다.

| 실조회 | 확인 결과 |
| --- | --- |
| 현재 기준, date 생략 | HTTP 200. 전체 보스 항목 82개, 주간 56개, 주간 등록 12개/미등록 44개, 주간 등록 여부 누락 0개 |
| 사용자 제공 보스 이름 대조 | 기대 12개/관측 12개, 누락 0개/추가 0개 |
| 등록 항목 매핑 | 12개 모두 내부 보스·난이도에 매핑 가능. 등록/미등록과 완료/미완료는 별개 값으로 확인 |
| 전체 카탈로그 대조 | 내장 54개 난이도가 현재 응답에 모두 존재. 매핑 누락 0개. 주간 응답의 추가 2개 항목은 내장 결정석 수익 대상으로 임의 편입하지 않음 |
| 같은 캐릭터, 응답 기준일의 7일 전 date 지정 | HTTP 200. 요청 날짜와 응답 날짜 일치. 등록된 12개 보스·난이도 집합이 현재와 동일 |

현재 성공 응답의 date는 7-C에서 확인한 KST 시각 접미사를 포함하는 형식이었다. 기존 정규화를 유지했다. 이번 7일 전 date 지정 요청은 성공했다. 따라서 7-C의 단일 date 지정 400을 모든 date 요청의 제한이라고 일반화할 수 없다. 그때의 400 원인은 이번에도 단정하지 않는다. API 레퍼런스 원문은 변경하지 않았다.

## 4. registration_flag / complete_flag 처리

- 등록 여부와 완료 여부를 별개로 읽고 관측 JSON에 보존한다. 완료=true라는 이유로 등록=true로 추정하지 않는다.
- 등록 여부가 없는 예전 v4 관측은 registered=null, UI에서는 등록 여부 미확인으로 처리한다. false나 등록 없음으로 바꾸지 않는다. DB 마이그레이션 없이 역호환한다.
- 새 응답의 명세 밖 플래그 값은 파싱 오류로 처리하며 기존 관리 설정·클리어를 변경하지 않는다.
- API 참고 영역은 현재 수동 관리 난이도와 기존 기록에 해당하는 관측만 보여주고 등록/미등록/미확인 및 완료 여부를 구분한다. 원본 전체 보스 목록을 관리 대상처럼 펼치지 않는다. 매핑 미확인 주간 항목은 건수와 반영 불가를 표시한다.
- registration_flag를 사용한 관리 목록 덮어쓰기·자동 동기화는 구현하지 않았다.

## 5. 자동 구성 가능 여부와 핵심 질문

| 질문 | 판단 |
| --- | --- |
| 등록된 보스만 추출 가능한가? | 가능. 실제 문자열 true/false가 모두 있었고 true인 주간 항목 12개를 구분했다. |
| 보스·난이도를 캐릭터별 관리 목록으로 쓸 수 있는가? | 기술적으로 후보 구성 가능. 현재 표본은 전부 매핑됐다. 단 한 캐릭터 표본이며 최종 도입은 보류한다. |
| 인게임 설정과 일치하는가? | 사용자 제공 보스 이름 12개는 일치. 사용자가 난이도는 기억하지 못한다고 밝혀 난이도까지 일치한다고 검증할 수는 없다. |
| 주간 초기화 후 등록이 유지되는가? | 현재/7일 전 등록 보스·난이도 집합이 같았다는 관측은 확보했다. 초기화 직전/직후 비교나 등록 변경 실험은 아니므로 일반적인 유지 규칙을 확정하지 않는다. |
| 등록 정보 없는 캐릭터는? | 실표본 없음. 전체 미등록, 플래그 누락, 빈 응답/미접속을 구분해야 한다. 지금은 기존 수동 관리 목록을 유지하며 자동으로 빈 목록을 저장하지 않는다. |
| 조회 실패 시 기존 목록 유지 가능한가? | 현재 구현은 조회와 수동 계획 저장이 분리되어 있어 가능하다. 파싱·HTTP·저장 오류만으로 계획/클리어를 변경하지 않는다. 빈 정상 관측 후에도 계획·기록·합계가 유지되는 합성 테스트도 통과했다. |

불확실성이 남은 상태에서 목록 자동 구성을 완성하지 말라는 요청에 따라 자동 구성/대체 모드를 새로 만들지 않았다. 수동 선택의 최종 제거도 하지 않았다.

## 6. 화면 정리 및 한계

기존 수동 계획을 기준으로 현재 관리 보스만 기본 클리어 영역에 표시한다. 관리 해제됐지만 기록이 있는 보스는 별도의 “현재 관리 대상 외 기록” 접힘 영역으로 옮겼다. 과거 기록은 수정 가능하며 합계 계산 정책도 그대로다. 가격·버전·출처·선택적 정정 사유는 “가격·기록 근거”에 모아 기본 표시를 줄였다. 수동 보스 선택 영역과 그 저장 방식은 유지했다.

이는 기존 관리 방식 안에서의 표시 정리다. 스케줄러가 관리 대상의 원천이 된 것은 아니다. 기록 당시 난이도는 해당 스냅샷대로 남으며, 사용자의 계획 변경이 과거 난이도/수익을 자동 수정하지 않는다.

한계는 한 캐릭터 표본, 인게임 난이도 미대조, 초기화 경계 및 등록 변경의 반영 지연 미검증, 등록 0개 캐릭터/미접속 실응답 미검증이다. 현재 카탈로그가 모두 응답에 있었다고 해서 다른 시점·캐릭터·신규 보스도 항상 포함된다고 보장하지 않는다. 이름·난이도·주기가 불확실하면 매핑하지 않는 기존 규칙을 유지한다.

## 7. 호출 횟수와 데이터 보호

**7-D 실제 넥슨 HTTP 호출은 총 2회**(현재 1회, 7일 전 1회)이며 모두 200이었다. 캐릭터 목록·기본 정보·이미지를 실조회하지 않았다. 추가 재시도는 없다. ignored 조사 테스트는 최대 두 관리 캐릭터와 과거 1건으로 제한되지만 이번에는 관리 캐릭터가 한 명이라 두 번만 호출됐다. 합성 테스트 및 Windows UI 검증은 오프라인 차단 모드로 추가 호출 0회다.

개발 키 파일의 존재·ignore·미추적 및 추적 이력 없음 확인 후, 실조회 테스트에서만 메모리로 읽었다. 개발 키를 사용자 Credential Manager에 등록하지 않았다. 사용자 키 저장 방식은 변경하지 않았다.

**SQLite 스키마는 v4 그대로이며 추가/변경 마이그레이션은 없다.** 사용자 DB는 읽기 전용 조사와 전후 해시 확인에만 사용했고 실제 앱 검증은 별도 OS 임시 DB를 사용했다. 사용자 DB SHA-256은 작업 전후 동일했다. 합성 v4 DB에서도 기존 설정 행과 스냅샷·revision·선택/계획이 유지됨을 확인했다. 기존 마이그레이션 001~004와 가격 JSON은 변경하지 않았다.

## 9. 다음 작업 제안 및 종료

1. 사용자가 확인 가능한 대표 캐릭터의 **인게임 난이도**를 등록 플래그의 보스·난이도와 대조한다. 보스 이름은 이번에 일치했다.
2. 별도 승인한 최소 조회로 목요일 초기화 직전/직후 또는 통제된 등록 변경 전/후를 확인한다. 이번에 추가 실호출하거나 인게임 설정을 변경하지 않았다.
3. 등록 0개·미접속·누락/매핑 불가·HTTP 실패일 때 기존 목록을 유지하는 동작을 확정한다. 자동 구성 도입 시 마지막 정상 목록을 저장하고, 빈 응답을 삭제 지시로 처리하지 않는 설계가 필요하다.
4. 위 검증과 정책을 확인한 뒤 명시적 “스케줄러 목록 가져오기”의 도입 및 수동 선택의 최종 제거 여부를 사용자 승인으로 결정한다. 이번 단계에서 구현하지 않았다.

**7-D의 기능 정리와 조사 결과를 보고하고 여기서 멈춘다. 자동 목록 구성을 임의로 완성하지 않으며 8단계 메소·아이템 및 UI 리디자인은 시작하지 않는다.**

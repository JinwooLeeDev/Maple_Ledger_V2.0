# 6단계 완료 기록 — 메인 대시보드와 캐릭터 카드

작업일: 2026-10-28. AGENTS, 아키텍처, 개발 계획, 5단계 보고서, API 레퍼런스와 기존 키·관리 선택·클라이언트를 확인했다. 외부 maplemate 스킬은 사용하거나 참고하지 않았다. 보스·수익 계산·아이템 기능은 구현하지 않았다.

## 구현한 화면

메인 화면을 저장된 관리 캐릭터 대시보드로 구성했다. 앱 제목, 설정 이동, 캐릭터 관리 이동, 카드 새로고침, 로딩·오류·관리 미설정 안내를 제공한다. 기존 조회·본캐 지정·관리 선택 화면은 캐릭터 관리로 유지했다.

카드는 이미지·닉네임·직업·레벨·월드와 본캐 여부를 표시한다. 본캐는 SQLite 위치 0을 따라 항상 첫 카드이고 테두리·배경·배지로 구분한다. 나머지는 저장된 순서다. 기본 Windows 창에서는 3열×2행으로 최대 6개를 배치하고 좁은 창에서는 2열/1열로 조정한다. 별도 UI 프레임워크나 디자인 시스템은 추가하지 않았다.

DB 정보로 카드를 먼저 표시한 뒤 카드별로 갱신한다. 한 카드의 오류로 다른 카드나 이전 데이터를 지우지 않는다. 공개 이미지가 없거나 다운로드·브라우저 디코딩이 실패하면 로컬 SVG 대체 이미지를 표시한다. 이전에 성공한 이미지가 있으면 유지하면서 이미지 오류를 안내한다.

## API 및 이미지 표시

공식 레퍼런스에서 `GET /maplestory/v1/character/basic`을 확인했다. 필수 쿼리는 ocid, 인증은 x-nxopen-api-key 헤더이고 date는 선택 사항이다. 이번에는 date를 생략하여 현재 정보를 조회한다. 필요한 응답 필드는 world_name, character_name, character_class, character_level, character_image다.

저장된 OCID를 사용할 수 있으므로 대시보드는 전체 character/list를 호출하지 않는다. Command는 SQLite에서 실제 관리 항목과 선택 revision을 확인하고 그 항목만 조회한다. 기존 NexonClient의 reqwest 연결·타임아웃·본문 상한·오류 처리를 재사용했다. API 키는 Rust가 Windows Credential Manager에서 읽으며 React에는 전달하지 않는다.

응답의 world_name이 저장된 월드와 다르면 새 정보를 적용하지 않는다. 이름·직업·레벨의 누락/null은 확보한 정보를 유지한다. 이 기본 정보 응답에는 account_id와 OCID가 없으므로 계정 소속이나 OCID 변경을 이름으로 추측하지 않는다. 요청한 저장 OCID를 그대로 사용하고 계정 소속 재확인은 기존 관리 화면의 전체 목록 조회 흐름을 따른다. 오류가 나도 관리 선택이나 기록을 삭제하지 않는다.

character_image의 URL은 HTTPS, 정확한 open.api.nexon.com 호스트, `/static/maplestory/character/look/` 경로만 허용한다. 리다이렉트는 기존 클라이언트에서 차단하며 이미지 요청에는 API 키를 붙이지 않는다. 응답의 래스터 서명(PNG/JPEG/GIF/WebP)과 크기를 검사하고 data URL로 인코딩하여 React에 전달한다. 원격 SVG는 허용하지 않는다. 본문 공통 상한은 2MiB이며 이미지의 최종 허용 상한은 1MiB다. 기존 CSP self/data 범위로 표시하여 외부 이미지 호스트 권한을 추가하지 않았다.

실제 Windows 검증에서 기본 정보 파싱과 공식 이미지 다운로드·브라우저 onLoad 표시가 성공했다. 실응답 전체를 별도 파일로 저장하지 않았다. 모델은 명세 외 필드를 무시하고 선택 필드 누락을 안전하게 처리한다.

## 로딩·갱신·캐시

- get_dashboard: SQLite 설정과 실행 중 메모리 캐시를 읽어 카드 목록·선택 revision 반환. 키 읽기나 API 호출 없음.
- refresh_dashboard_card: DB 관리 대상과 revision을 확인하고 해당 OCID의 기본 정보/이미지만 갱신.
- 정상 정보는 15분, 실패는 60초 동안 자동 진입 요청에 재사용한다. 명시적 새로고침은 갱신하되 2초 이내 반복은 재사용한다. 이는 앱 로컬 정책이며 넥슨 공식 쿼터값이 아니다.
- 같은 이미지 URL은 이미지를 다시 다운로드하지 않는다. 변경 URL 실패 시 이전 이미지를 새 URL의 성공 이미지로 잘못 간주하지 않도록 다운로드에 성공한 URL만 캐시에 기록한다.
- 캐시는 관리 목록에 남고 식별자가 같은 최대 6개만 유지한다. 키 저장/삭제 시 초기화한다. 이미지와 기본 정보는 영구 저장하지 않는다.
- React 효과는 화면 진입·명시적 새로고침에만 실행하고 렌더링에는 실행하지 않는다. OCID/revision별 pending promise와 Rust 잠금·캐시로 StrictMode·동시 호출을 합친다.
- 파싱·네트워크·월드 식별 불일치는 카드별로 안내한다. 공유 키 오류/429는 남은 배치 호출을 중단한다. 429는 대기 안내와 백엔드 차단을 적용하고 자동 재시도하지 않는다.

SQLite 스키마 2, 테이블 및 마이그레이션은 변경하지 않았다. 카드 코드에서 DB 쓰기나 선택 삭제를 하지 않는다. 앱 재실행 후 저장된 표시 정보·순서·본캐를 복원하고, 메모리 캐시가 없으므로 관리 캐릭터의 기본 정보·이미지를 다시 조회한다. 오프라인 재실행 때는 저장된 표시 정보와 대체 이미지를 사용할 수 있다.

## 실제 호출 횟수

저장된 본캐 1개를 사용했다. 에이전트 검증 중 실제 넥슨 요청은 다음과 같다.

| 경로 | 횟수 | 목적 |
| --- | ---: | --- |
| character/basic | 3 | 첫 화면 1, 수동 새로고침 1, 앱 재실행 1 |
| 공개 캐릭터 이미지 GET | 2 | 첫 표시 1, 앱 재실행 1 |
| character/list 및 기타 API | 0 | 저장 OCID로 충분하여 호출하지 않음 |

총 HTTP 요청은 5회(인증 API 3회 + 키 없는 공개 이미지 다운로드 2회)다. 캐릭터 관리 화면 왕복과 일반 렌더링에서는 증가하지 않았다. 수동 새로고침에서도 같은 이미지 URL은 재사용하여 다운로드가 늘지 않았다. 이 횟수는 선택적으로 켠 debug 집계에서 확인했으며 URL·키·OCID·계정 ID는 출력하지 않았다. 별도 독립 live 테스트를 중복 실행하지 않았고 개발 TXT 키도 읽지 않았다.

## 추가 의존성과 파일

Rust의 base64 0.23.1을 직접 선언했다. 기존 reqwest 전이 의존성에 있던 패키지를 재사용하므로 신규 패키지 다운로드나 새 버전 추가는 없었다. data URL을 사용하면 바이트 배열보다 작은 IPC 전달과 메모리 이미지 재사용이 가능하다. 대안인 원격 img URL 직접 표시는 별도 외부 CSP 및 이미지 재다운로드 제어가 필요해 선택하지 않았다. 새 npm 의존성은 없다. [base64 공식 사용법](https://docs.rs/base64/0.23.1/base64/)을 확인했다.

실제 6캐릭터의 이미지를 받기 위해 사용자 선택을 임의로 늘리거나 추가 API를 호출하지 않았다. 최대 6개·순서·독립 오류는 합성 Rust/SSR 테스트로 검증했고 실제 Windows에서는 현재 저장된 1캐릭터의 이미지와 핵심 흐름을 확인했다. Windows에서 모든 네트워크·이미지 실패를 각각 강제로 재현한 것은 아니다. 최종 공통 키/429 배치 중단 안내 보완 후에는 합성 렌더링·타입 검사를 다시 수행했으며 정상 이미지 경로는 변경하지 않았다.

개발 앱 빌드는 1회(약 13.35초)만 수행했고 재실행은 같은 실행 파일을 사용했다. 테스트 전후에 무관한 전체 테스트·production/release 빌드·배포 패키징을 하지 않았다. 추가 테스트 코드는 앱 종료 후 작성하여 워처 재빌드를 유발하지 않았다. 높은 Windows DPI의 창은 DPI-aware 캡처로 확인했으며 임시 캡처·집계 로그·실행 서버는 정리했다. Git 커밋/푸시는 하지 않았다.

## 남은 과제와 7단계 설계 방향

- 이미지 캐시는 실행 중 메모리 한정이다. 오프라인 재실행 시 이전 이미지를 복원하는 영구 캐시는 이번 범위에 없다.
- 기본 정보 응답으로 계정 ID를 재검증할 수는 없다. 계정/월드 소속 변경은 관리 화면의 전체 목록 검증을 사용하며 임의로 기록을 재연결하지 않는다.
- 좁은 창에서는 반응형 열 수가 줄어 스크롤이 필요할 수 있다. 기본 Windows 창은 3열 구성이다.
- 다음 7단계는 보스/난이도·클리어 기록·결정석 보상·초기화 규칙을 먼저 설계한다. 가격의 공식 출처·적용일·파티 분배, 스케줄러 관측과 수동 기록 우선순위, 기간별 이력 보존 및 수익 중복 반영 방지를 확정한다. 검증되지 않은 금액·초기화 시각을 하드코딩하지 않는다.

6단계 완료 후 멈추고 사용자 승인을 기다린다.
